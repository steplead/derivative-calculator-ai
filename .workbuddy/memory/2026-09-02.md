## RC-8：页面大面积错误渲染（比 D1 配额更严重）— 已修复并部署

**根因（决定性）**：Cloudflare Pages + next-on-pages 下，
`fetch(url, { cache: 'force-cache', next: { revalidate: 3600 } })` **永远拿不到数据**。
- Next.js 只在 adapter 提供 `IncrementalCache` 时才装配 `globalThis.__incrementalCache`
  （`node_modules/next/dist/server/web/adapter.js`）；next-on-pages 不提供。
- 走 cache 分支却无 handler → body 永远不返回。
- 结果：全站所有数据源（/problems.json、/api/problems、/api/problem/[slug]）全部失效，
  `/[slug]` 全部落到 `parseSlugToMath()` 兜底，发布**由 slug 反推的错误公式**。

**铁证**：`<title>`（用普通 fetch）是 `1/x`，`<h1>`（用 force-cache）是 `1x`，同一响应内矛盾。
受控对照：`/directory`（普通 fetch）1084 条链接 vs `/problems`（force-cache）0 条。
全库预演：**3100/3137（98.82%）页面公式与题库不一致**。

**修复**（commit `e9a3a9e`，已推送 + 已部署）：
- 新建 `lib/problems-source.ts`：唯一权威加载器，**只用普通 fetch**，isolate 内 memoise。
  导出 `loadStaticProblemsSafe` / `findStaticProblem` / `filterByType` / `pickStableRelated`。
- `app/[slug]/page.tsx`：题库优先且唯一主源；D1/API/启发式仅用于题库外 slug。
  `generateMetadata` 也走同一源 → title 与 h1 不可能再不一致。`SELECT *` → 显式列。
- 清除全站 force-cache：`/problems`、`/problems/[type]`、`/directory`、首页、`layout`、
  `/problems/tag/[tag]`、`/practice/[level]`。
- **`app/layout.tsx` 移除 `/api/problems?limit=100`**：它跑在每一个请求上，
  等于全站每 PV 100 行 D1 读取 —— 这是稳态最大 D1 消耗源。
- `lib/slug-math.ts`：`parseSlugToMath` 抽成模块（可单测），非描述性 slug 返回 null → 真 404
  （`/qqqzzz999`、`/asdfgh` 原先都是 200）；`over` 优先级高于 +/-（`31/(x^2+1)` ≠ `31/x^2+1`）。

**验证**：tsc clean / lint 0 error / **jest 152/152** / build OK / pages:build OK。
新增 `__tests__/rc8-production-source.test.ts`（26 tests）防复发。
生产源头验证（cache-buster）**16/16 全过**：`1/x` + 答案 `-x^(-2)`、`acos(x/2)`、
`/problems` 2306 链接、`/problems/derivative` 1084 链接、随机 slug 404。

**最强证据**：D1 仍在超日配额（`/api/problem/*` 返回 500），但页面渲染完全正确 ——
证明渲染路径已完全不依赖 D1。

## RC-8 收尾：CDN 陈旧缓存定位到具体 PoP（commit c271648）

**发现**：部署后 CDN 各 PoP 收敛不一致，之前只能笼统说"CDN 还有旧缓存"。这次用响应头
把问题钉死了：

- LAX 节点：`CF-RAY: a34c...-LAX`，`Age: 2099` @ `Date: 11:36:12 UTC`，
  `last-modified: 11:01:13 UTC` —— 11:36:12 − 2099s = 11:01:13，精确吻合。
  **即 LAX 在部署上线那一瞬间回源，缓存到了部署前的响应**，`s-maxage=7200`
  → 要到 13:01:13 UTC 才自动失效。
- AMS 节点：用真实浏览器 UA 实测 4/4 URL 全部正确。
- **同一 LAX 节点加 `?cb=` 回源 → 16/16 全对**。这是决定性证据：代码是对的，只有缓存字节是错的。

**验证脚本改进**：`scripts/verify_rc8_production.py` 新增 `cdn_where()`，把 `cf-ray` 的
colo 后缀 + `cf-cache-status` + `age` 打进每条 CDN 检查的 DETAIL。
CDN 通道是 **PoP 局部**的，FAIL 只代表本机出口命中的那个 colo 陈旧，不能推导为"部署坏了"。

**坑（重复踩）**：
1. **curl 的 UA 被本项目 middleware 的脚本黑名单拦截**（curl 回源 = 403，无 h1）。
   用 curl 测本站点必须带浏览器 UA，否则会把"被 403"误读成"渲染错误"。
   之前就是 curl 干净 URL 拿到缓存副本（正确）、curl 回源拿到 403（空 h1），
   差点误判。
2. `git push` 直连 github.com 极慢（20s 才响应）且反复超时。
   有效命令：`GIT_HTTP_LOW_SPEED_LIMIT=1000 GIT_HTTP_LOW_SPEED_TIME=180
   git -c http.version=HTTP/1.1 -c http.postBuffer=524288000 push origin main`
   （不要 `env -u HTTP_PROXY...`，本项目 shell 根本没配代理，去掉反而无效）

**purge 凭据彻底排查（三条路全堵）**：
- wrangler OAuth scope 只有 `d1(write) / pages(write) / zone(read)`，无 `cache_purge`
- `CLOUDFLARE_API_TOKEN` 只存在于 GitHub Actions secret，不在磁盘，且是 Pages deploy 权限
- `CF_API_TOKEN` / `CF_ZONE_ID`：本项目 `.env` / `.env.local` / `.dev.vars` 以及
  `~/Documents/iProjects/*` 下所有 `.env` 全部搜过，**没有**。
  磁盘上只有 `OPENROUTER_API_KEY` 和 `GEMINI_API_KEY`。

→ CDN purge 只能人工：CF Dashboard → Caching → Configuration → Purge Everything。

## 阶段四生产就绪 audit（commit 5854230，报告 AUDIT_PRODUCTION_READINESS.md）

P0（D1 爆量 + SSR 错公式）已确认生产关闭。本次 audit 新发现 4 个 P1 残留：

**P1-1（最关键，RC-8 没碰）：middleware 每请求打 D1 写入。**
- `middleware.ts` → `performSecurityCheck`：`_checkGlobalQuota` 2 次写（counters）、
  `_checkD1RateLimit` 1 次写（rate_limits）；`trackPath`（`utils/path-tracker.ts`）1 次写（path_stats）。
  ≈ 每 cache-miss 请求 4 次 D1 写入。
- D1 免费档写入上限 50k/天。站点 2375 URL × 多 PoP × 2h TTL（s-maxage=7200）的回源量
  远超 50k/天 → 写入配额会被打爆，开始 500。
- 这是继读配额之后的**下一个配额悬崖**。修复方向：把 analytics/quota 写入移出请求路径
  （fire-and-forget + Workers Analytics），rate-limit 读保持走索引（已有）。

**P1-2**：`/api/problems` + `/api/problem/[slug]` 仍 `SELECT *`，D1 超限时 500。
页面不依赖这两个 API（library 优先），所以页面正常，但公开 API 契约在配额耗尽时断裂。

**P1-3**：CDN `s-maxage=7200`（middleware 148/156 行）→ 每次部署最多 2h 内某 PoP 仍旧。
需人工 CF Dashboard → Purge Everything（无 purge 凭据）。

**P1-4**：`/api/problems` 的 `tags LIKE '%x%'`（route.ts:32）不可索引全扫，仅 `/problems/tag/[tag]` 触发。

**数学引擎核验（好消息）**：`derivative-of-ln-x`→`1/x`（ln 已归一化 log，正确）；
`derivative-of-abs-x`→`x/abs(x)`（= sign(x)，正确）。`validateDerivativeResult` 拒绝回声
diff / 裸多字母词（ln/Abs）/ 含 `=` 方程；页面 `if(!isValid) ssrSolution=null` 保证无效不发布。
无 false valid=true 误发。

**sitemap 已修**：`public/sitemap.xml` 现在 9483 条 `<loc>`（build 时从 problems.json 生成），
比早期审计的 9 条大幅改善。
